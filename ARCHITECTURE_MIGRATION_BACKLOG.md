# SMRITI — Architecture Compliance Migration Backlog

Generated by scanning the actual repository (524 non-test `.py` files under `smriti_retail_os/`) against the four-layer pattern already defined in `ARCHITECTURE.md` §9 (`www → api → service → repository → ERPNext`), refined per this rule:

> **API and www files must contain no persistence calls at all.**
> **Service files may use frappe framework utilities (`frappe.throw`, `frappe.db.exists`, `frappe.utils`, permissions) but must not persist directly.**
> **Only `repositories/` and `adapter/` modules may call `frappe.get_doc()`, `frappe.new_doc()`, `frappe.db.sql()`, `frappe.db.set_value()`, `frappe.db.commit()`, `frappe.db.delete()`, `frappe.delete_doc()`.**

## Headline numbers

- **83 of 524 files (16%)** violate the persistence-boundary rule above.
- Those 83 files contain **844 individual persistence calls** that should live in a repository/adapter instead.
- Split fairly evenly across layers: **42 of 65 api-layer files** and **41 of 76 service-layer files** violate the rule.
- Only **3 modules** (`pos_profile`, `item_studio`/product, `purchase_studio`) have any repository or adapter layer at all — and even two of those three still leak persistence calls in their own `api`/`service` files, so "has a repository folder" is not the same as "fully compliant."

Reference implementation to copy the pattern from: `api/pos_profile_api.py` → `services/pos_profile_service.py` → `repositories/pos_profile_repository.py`.

## Suggested sequencing

1. **Sprint 0:** Land the CI enforcement script (`check_architecture_boundaries.py`, included alongside this doc) so the backlog can only shrink from here, not grow.
2. **Sprint 1:** Tier P0 (11 files) — money/license/security. Use `pos_profile` as the template.
3. **Sprint 2–3:** Tier P1, starting with the PSV family as one cohesive migration, then the remaining high-traffic APIs (barcode, reports, item master, master, setup wizard).
4. **Sprint 4:** Tier P2 — start with `purchase_studio` since the adapter already exists; then `cge_service.py`.
5. **Ongoing:** Tier P3 as a backlog of small tickets, picked up opportunistically once CI prevents regression.
