# ADR-0009: SMRITI Platform Primitives and Services Standard

## Context & Motivation

As SMRITI Retail OS evolves, multiple frontend business modules (Studios) require overlapping operational capabilities (e.g., printing labels, dispatching SMS/WhatsApp notifications, executing payment integrations, and calculating coverage metrics). 

If every studio implements its own printing connections, notification clients, or database transaction logs, the codebase becomes bloated, maintenance costs escalate, and architectural debt multiplies.

To build a scalable retail OS, SMRITI must separate **Business Modules** (user-facing workflow interfaces) from **Platform Services** (reusable, printer-agnostic, and channel-neutral capability engines).

---

## Decision

SMRITI formally registers a dual-layered architecture classifying components into either **Platform Services** or **Business Modules**:

```
                  SMRITI BUSINESS MODULES
   ┌───────────────────┬───────────────────┬───────────────────┐
   │  Barcode Studio   │   Label Studio    │    POS Studio     │
   └─────────┬─────────┴─────────┬─────────┴─────────┬─────────┘
             │                   │                   │
             └───────────────────┼───────────────────┘
                                 ▼
                     SMRITI PLATFORM SERVICES
   ┌───────────────────────────────────────────────────────────┐
   │  Print Framework    Notification Engine   Payment Engine  │
   │  Formula Engine     Workflow Engine       Token Registry  │
   └───────────────────────────────────────────────────────────┘
```

### 1. Platform Primitives Registry
The platform architecture consists of the following core engines:
* **Print Framework**: Abstracts physical connections (USB, LAN, Bluetooth, QZ) and manages asynchronous `SMRITI Print Job` lifecycles.
* **Notification Engine**: Integrates and multiplexes transactional SMS, WhatsApp, and email gateways.
* **Payment Engine**: Interfaces with credit cards, UPI, wallets, and POS terminal adapters.
* **Formula Engine**: Manages central registrations, execution rules, and audits for business metrics.
* **Token Registry**: Resolves data bindings for print layouts and reports dynamically.

### 2. Architecture Boundary Constraints
1. **Agnostic Design**: Platform services must remain completely decoupled from business entities. For example, the `Print Framework` does not process `Item Code`, `Customer`, or `Store` records; it accepts only neutral print streams (ZPL, TSPL, PDF) and dispatch meta.
2. **Unified API boundaries**: Studios must never manipulate connection sockets or notification queues directly. All interactions must proceed via the whitelisted platform API controllers.
3. **Repository Pattern Enforcement**: Platform services must adhere to `ADR-0002`, routing database queries through dedicated repositories.

---

## Consequences

* **Decoupled Extensions**: Developers can add support for new hardware drivers (e.g. Bluetooth BLE, Cloud Printer) by updating a connection adapter in the `Print Framework` without touching any of the business studios.
* **Reduced Code Duplication**: Standard features like print history log, retry queue, and notification delivery receipts are implemented once and reused across all studios.
* **Clean Quality Checks**: Testing boundaries are simplified by mocking the platform dispatcher layer.
