# ADR-0002 — SMRITI Business Layer Independence

- **Status:** ACTIVE
- **SPC Violated:** None (General Architecture)
- **Severity Level:** Critical
- **Author:** Jawahar R. Mallah
- **Date Created:** 2026-07-04
- **Expiry Condition:** Permanent (Stable Architecture)

---

## Context and Problem Statement

In standard Frappe and ERPNext applications, backend controllers and server-side scripts often mix API routes, validation rules, financial calculations, and direct database queries (e.g. `frappe.get_doc()`, `frappe.db.sql()`, `frappe.new_doc()`) in a single layer. 

In SMRITI Retail OS, this tight coupling creates severe risks:
1. **Lack of Testability**: Service layer logic cannot be tested without establishing a live MariaDB database and site context.
2. **Upgrade Friction**: Database schema changes in ERPNext or Frappe core directly break SMRITI business logic.
3. **Domain Pollution**: Domain boundaries are blurred when business rules, validations, and database writes are mixed together.

---

## Decision

To enforce decoupling, SMRITI implements the **Repository Pattern** and separates business logic from persistence:

1. **Service Layer Purity**:
   - Files under `service/`, `services/`, and matching patterns `*_service.py`, `*_engine.py`, or `*_kernel.py` MUST NOT contain direct database persistence calls.
   - Specifically, the following direct calls are forbidden in the business and API layers:
     * `frappe.get_doc()`
     * `frappe.new_doc()`
     * `frappe.db.sql()`
     * `frappe.db.set_value()`
     * `frappe.db.commit()`
     * `frappe.db.delete()`
     * `frappe.delete_doc()`

2. **Isolated Repository Layer**:
   - All persistence reads and writes must be isolated inside repositories (located under `repositories/`, `repository/`, or `adapter/` directories).
   - Servicing layers must interact with the repository layer to query or persist data.

3. **Static CI Gate Enforcement**:
   - This architectural decision is statically enforced by [smriti_architecture_guard.py](../../apps/smriti_retail_os/smriti_architecture_guard.py).
   - Any new file or modified file introducing forbidden persistence calls in the API/service layer will trigger a validation block and fail the release gate.

---

## Consequences

- **Enforceable Architecture**: Decoupling is no longer aspirational; it is validated programmatically on every commit.
- **Improved Test Coverage**: Repositories can be cleanly mocked or replaced with in-memory adapters for fast, database-free unit testing.
- **Controlled Baseline**: Existing legacy violations (totaling 770 across 87 files) are locked in [architecture_baseline.json](../../apps/smriti_retail_os/architecture_baseline.json). The ratchet policy ensures this number can only decrease.
