# ADR-0008 — Barcode Studio Modularization

- **Status:** ACTIVE
- **SPC Violated:** None
- **Severity Level:** Major
- **Author:** Jawahar R. Mallah
- **Date Created:** 2026-07-04
- **Expiry Condition:** Permanent (Stable Architecture)

---

## Context and Problem Statement

The SMRITI Barcode Studio was originally implemented as a monolithic structure. 
1. **Backend Monolith**: `barcode_api.py` contained 2,644 lines of code combining API routes, raw database persistence operations, layout ZPL/TSPL coordinate calculations, diagnostics, and telemetry logs. This violated the *Service-First Design* principle (Rule 2) and made test isolation impossible.
2. **Frontend Monolith**: The `www/barcode.html` page contained 4,899 lines of embedded JavaScript and CSS. This caused high code complexity, unmaintainable UI code, and slow asset compilation.

We needed a clean, decoupled design where API routing, business services, token rendering, and client-side view management are separated into dedicated, single-responsibility files.

---

## Decision

We resolved to split the backend logic and modularize the frontend assets into decoupled, single-responsibility modules:

1. **Backend Refactoring (`smriti_retail_os/barcode/`)**:
   - `barcode_api.py` is refactored into a thin routing shell.
   - Introduced `token_registry.py` to manage dynamic token resolution and metadata caching.
   - Decoupled business logic into separate services: `item_service.py`, `prn_generator.py`, `printer_service.py`, `analytics_service.py`, `template_service.py`, `batch_service.py`, `diagnostics_service.py`, and `telemetry_service.py`.

2. **Frontend Refactoring (`public/js/barcode/` & `public/css/`)**:
   - Extracted stylesheet to `public/css/barcode_studio.css`.
   - Split JavaScript code into 10 decoupled modules:
     - `barcode_core.js` (global state and pub/sub events)
     - `barcode_qz.js` (QZ tray printer connection)
     - `barcode_items.js` (worksheet item management)
     - `barcode_queue.js` (asynchronous printing queue)
     - `barcode_preview.js` (canvas rendering preview simulator)
     - `barcode_designer.js` (drag and drop label designer logic)
     - `barcode_print.js` (print layout compile instructions)
     - `barcode_jobs.js` (print job history metadata)
     - `barcode_analytics.js` (print queue telemetry graphs)
     - `barcode_init.js` (entry-point script initializer)

3. **Verification and CI Guard**:
   - Created `tests/test_prn_regression.py` to compare TSPL/ZPL layouts produced by new services against raw legacy API baseline output.

---

## Consequences

- **Maintainability**: Modularity improved code readability, reducing `barcode.html` page complexity from 4,899 lines to 1,080 lines.
- **Architectural Health**: Removed direct database queries from the API layer, reducing the SMRITI Architecture Guard violations from 836 to 770 (a 7.9% overall reduction).
- **Extensibility**: The decoupled Token Registry can be directly imported and reused by other layout modules (e.g., a future Label Studio).
- **Bundling/Caching**: Frontend assets are cache-busted using version parameters (`?v=2.1.1`) and compiled under esbuild production bundling.
